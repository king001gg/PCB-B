## 1. 结论摘要

**当前版本不建议直接上线。** 24 项已核实缺陷中有 3 项会直接改变 OK/NG 判定或阻断数据链路，且都落在生产主路径上。

| | 结论 |
|---|---|
| 测试套件 | **1073 passed / 1 skipped / 35 xfailed / 0 failed**，退出码 0，耗时 123.6 s |
| 语句覆盖率 | **总计 58%**（3973 语句 / 1653 未覆盖） |
| 非 UI 覆盖率 | **88.9%**（2609 语句 / 289 未覆盖） |
| UI 覆盖率 | 0%（1364 语句，按约定排除，见 §5） |
| 缺陷总数 | **24 项已核实**（对应 35 条 xfail 回归用例） |
| 严重度分布 | P0 × 3、P1 × 4、P2 × 8、P3 × 9 |

**三条最重要的结论：**

1. **粗糙度维度（权重 0.30，五维最大）已完全失效并方向反转。** 实测 6 种板卡的粗糙度得分取值集合只有 `{0.0, 100.0}`：正常喷砂面得 **0 分**，完全平坦（= 未喷砂）的面得 **100 分**。该维度对所有已粗化表面恒为 0，把总分上限从 100 压到 70 —— 实测正常板卡只有 66.9，距 NG 阈值 60 仅剩 6.9 分余量。既误判 NG，又对真正的粗糙度差异毫无分辨力。
2. **报告 JSON 导出在「判 OK 的板卡」上 100% 失败**（`TypeError: Object of type bool is not JSON serializable`），而判 NG 的板卡反而正常。导出、追溯、SPC 这条链路对合格品是断的。
3. **灰度输入 + 检出任意缺陷 → `run()` 崩溃**，且失败方向是反的：良品（无缺陷）跑得通，检出缺陷反而抛异常。相机默认输出 `Mono8`，这是默认配置下的主路径。

本报告中每一条缺陷都满足三个条件，缺一不可：

1. **在生产对象上复现**，不是构造的替身；
2. **归因到具体代码行**，能解释「为什么必然发生」而非「恰好发生了」；

### P0

#### A1. 粗糙度维度口径不一致 → 30% 权重失效且方向反转

**位置**：`core/texture.py:756-758`（生产方）× `core/quality.py:290-292`（消费方）

`compute_cv_heatmap()` 返回的是**按自身 95 分位归一化**后的图：

```python
cv_max = np.percentile(cv_map[valid], 95)
cv_map = np.clip(cv_map / cv_max, 0, 1)
```

所以它的均值是一个**相对量**，天然被顶到 0.7~1.0。而 `_score_roughness()` 拿这个均值去和**绝对**阈值 `roughness_cv_max: 0.35` 比较。两个口径对不上。

**实测**（真实 `InspectionPipeline`，三通道输入避开 C1）：

| 板卡 | CV 图均值 | 粗糙度分 | 总分 | 判定 | 缺陷数 |
|---|---|---|---|---|---|
| 正常喷砂面 seed=42 | 0.9549 | **0.0** | 66.9 | OK | 5 |
| 纹理偏强 texture=45 | 0.9595 | **0.0** | 55.0 | NG | 168 |
| 强噪声 texture=90 | 0.9577 | **0.0** | 66.3 | OK | 6 |
| 带氧化斑 4 块 | 0.5989 | **0.0** | 66.4 | OK | 6 |
| 带磨料嵌入 12 粒 | 0.9603 | **0.0** | 64.0 | OK | 16 |
| 完全平坦 texture=0 | 0.0000 | **100.0** | 85.0 | NG | 1 |

6 种板卡的粗糙度分取值集合 = `{0.0, 100.0}`。

**三重后果：**

1. **不分辨**：30% 的权重对所有已粗化表面恒为 0，好的坏的拿一样的分。
2. **方向反转**：纹理越充分 → CV 图均值越高 → 分越低；唯一拿满分的是**完全平坦**（即完全未喷砂）的表面。该板卡这次判 NG，靠的是「未粗化」缺陷触发硬阈值 —— 也就是说粗糙度维度**既不奖也不罚，只负责把总分上限从 100 压到 70**。
3. **余量被吃光**：阈值 `ok_score_threshold: 60`。五维中其余四维全满分时总分上限也只有 70，实测正常板卡 66.9 —— 只剩 6.9 分余量，其余任一维度轻微波动就会把良品判成 NG。

**修复建议**：二选一，不要两边都改。

- 方案 A（推荐，改动小）：`compute_cv_heatmap()` 增加 `normalize=False` 参数，质量评估传 `False`，让评分拿到原始 CV；
- 方案 B：保留归一化，把 `roughness_cv_max` 重新标定为相对量（如 0.9），并在 `default.yaml` 注明该阈值的口径。

无论哪种，都必须补一条**单调性**用例：粗糙度分随 `texture` 参数单调下降，且正常喷砂面严格优于完全平坦面。

#### A7. `ok_ng` 泄漏 `numpy.bool_` → 报告 JSON 导出在合格品上必崩

**位置**：`core/quality.py:255`（源头）
**传播**：`core/pipeline.py:202` → `core/reporter.py:49` / `ui/workers.py:104`

```python
report.ok_ng = report.overall_score >= self.ok_score_threshold
```

`overall_score` 是 `np.float64`，与 `int` 比较时由 NumPy 接管，结果是 `np.bool_` —— **它不是 `bool` 的子类**，`json.dumps` 直接抛 `TypeError`。

**实测**：

| 板卡 | 判定 | `ok_ng` 类型 | `isinstance(bool)` | 赋值来源 | JSON 导出 |
|---|---|---|---|---|---|
| 正常喷砂面 | OK | `numpy.bool` | **False** | 总分比较 `quality.py:255` | **TypeError** |
| 氧化斑 4 块 | OK | `numpy.bool` | **False** | 总分比较 `quality.py:255` | **TypeError** |
| 完全平坦 | NG | `builtins.bool` | True | 硬阈值 `quality.py:208/214` | OK |

失败信息：`TypeError: Object of type bool is not JSON serializable`

**注意这个非对称性**：走硬阈值判 NG 的板卡赋的是 Python 原生 `False`（`quality.py:208/214`），导出正常；只有走总分判定的板卡才污染。而生产上绝大多数板卡走的是总分判定 —— 也就是说**合格品导出崩、不良品导出正常**，正好是最不该出错的方向。同一份缺陷还会经 `pipeline.py:202` 传到 `InspectionResult.ok_ng`，并经 `ui/workers.py:104` 进 Qt 信号。

**为什么这个缺陷能活下来**（值得记下来）：NumPy 2.x 里 `type(np.True_).__name__` 就是 `'bool'`。任何靠 `type(x).__name__ == "bool"` 做的自检都会得出「类型正常」的结论 —— 本次测试中我方的一个探针脚本就先被骗过一次，只有 `isinstance(x, bool)` 或 `type(x).__module__` 能区分。

**修复建议**：在 `quality.py:255` 加 `bool(...)`。

```python
report.ok_ng = bool(report.overall_score >= self.ok_score_threshold)
```

必须修在源头。在 `reporter.py` 里逐字段兜底会漏掉 `InspectionResult.ok_ng` 和 `compute_spc()` 里的 `current > ucl`（`core/reporter.py:198`，同类问题）。已验证：在 `assess()` 出口单点加 `bool(...)` 后，`InspectionReport.to_json()` 立即正常输出完整 JSON（2.2 KB 量级，字节数随耗时字段浮动）。

#### C1. 灰度输入 + 检出任意缺陷 → `run()` 崩溃（且失败方向反转）

**位置**：`core/pipeline.py:212` → `core/defects.py:467`

```python
# pipeline.py:212 —— 把二维的 result.gray 原样传给绘制函数
annotated = self.defect_detector.draw_defects(image, defects)

# defects.py:467 —— 该赋值只在三通道图上成立
overlay[d.mask > 0] = color
```

`run()` 的 docstring（`pipeline.py:127`）明确声明支持 `灰度 (H, W)` 输入，相机默认 `pixel_format: "Mono8"` 也正是这个形态。

**实测**：

```
输入：shape=(256,256) dtype=uint8 通道数=1
run(灰度图)              → ValueError: NumPy boolean array indexing assignment
                            cannot assign 3 input values to the 48156 output values
                            where the mask is true
run(灰度图, 检测器全关)   → 跑通，缺陷数=0
run(同一张图的三通道版本) → 跑通，缺陷数=5
```

**失败方向是反的**：良品（检不出缺陷）静默跑通并判 OK，真正检出缺陷的板卡反而抛异常。产线上表现为「设备时好时坏」，且崩的时候恰好是有缺陷的时候 —— 缺陷品会绕过判定直接变成一次崩溃。

**修复建议**：`pipeline.py:212` 传入前统一通道数（灰度→`cv2.cvtColor(..., COLOR_GRAY2BGR)`），或在 `draw_defects()` 内部按 `overlay.ndim` 分支。推荐后者 —— 让绘制函数自己决定画布形态，避免每个调用点各转一次。

### P1

#### G1. PLC 写失败被静默吞成成功

**位置**：`hardware/plc.py`（`signal_ok` / `signal_ng` / `reset`）

`write_coil()` / `write_register()` 在失败时**不抛异常、只返回 `False`**（`ModbusRTUClient.write_coil` 源码中 `raise` 出现 **0 次**），而 `signal_*` 只在捕获异常时返回 `False`，从不检查返回值。异常分支因此是**不可达代码**。

**实测**（把 `plc.enabled` 置 `True` 才会真正走到总线 —— 默认配置下 `signal_*` 直接 `return True` 不碰总线）：

```
signal_ok(90.0)     -> 返回 True   期间失败的写操作 = 4 次   ← 谎报成功
signal_ng(20.0, 5)  -> 返回 True   期间失败的写操作 = 5 次   ← 谎报成功
signal_busy()       -> 返回 True   期间失败的写操作 = 3 次   ← 谎报成功
signal_alarm(3)     -> 返回 True   期间失败的写操作 = 2 次   ← 谎报成功
reset_signals()     -> 返回 True   期间失败的写操作 = 4 次   ← 谎报成功
共 18 次写操作全部返回 False，五个接口全部返回 True
```

**对照**（真实 `ModbusRTUClient`，从未 `connect()`，`_client is None`）：

```
real.write_coil(0, True)  -> False   ← 写操作自己知道失败了
real.signal_ok(90.0)      -> True    ← 上层却被告知成功
```

日志会打出「[PLC] OK 信号已发送 (评分=90.0)」，而线圈没有动。

**可达性**：`config/default.yaml` 里 `plc.enabled` 是 **`False`**，且该模块未被任何生产代码引用（见 G2），所以**今天不会触发**。但这两个前提都是配置项，任一被改动就立刻变成静默的安全失效 —— 定级 P1 是针对「一旦启用」的后果，不是当前正在发生的事故。

**修复建议**：`write_coil`/`write_register` 失败时抛异常（与 `signal_*` 现有的异常处理逻辑吻合，改完异常分支立刻变成可达），或让 `signal_*` 检查返回值并聚合。前者更彻底。

#### F2. 非 ASCII 路径：`cv2.imread` 失败 / `cv2.imwrite` 静默失败

**位置**：`main.py:150`、`main.py:210`、`ui/main_window.py:491`、`core/acquisition.py:129`、`utils/detector.py:70`

OpenCV 在 Windows 用 ANSI `fopen`，中文路径下：

- `cv2.imread('喷砂样品_甲.png')` → 返回 `None`（文件确实存在、确实是合法 PNG）→ 走上「无法读取图像」分支，退出码 1；
- `cv2.imwrite(...)` 到中文目录 → 返回 `False` **且不抛异常**，而 `main.py:210` 没有检查返回值 → 结果图**默认不保存**，用户要等到事后找文件时才发现。

**实测**：两个方向各有独立 xfail 用例（读路径崩溃、写路径静默丢失）。

**修复建议**：统一改为 `cv2.imdecode(np.fromfile(path, np.uint8), ...)` / `cv2.imencode(...)[1].tofile(path)`。建议封装成 `utils/image_io.py` 的两个函数，避免 5 个调用点各修一遍。同时给 `imwrite` 的替代实现加返回值检查。

#### G6. `_expand_cti_paths` 对带引号/空白的单值路径按冒号切碎

**位置**：`hardware/camera.py:109-113`

```python
elif ":" in raw and not (len(raw) > 1 and raw[1] == ":"):
    parts = raw.split(":")
```

盘符保护只看**第 2 个字符**。值被引号或空格包住后 `raw[1]` 变成 `"` 或空格，保护失效；而 Windows 路径里的冒号让 `":" in raw` 成立 → 按冒号切碎。

**实测**（producer 目录真实存在、内含真 `.cti` 文件）：

| 写法 | 结果 |
|---|---|
| 裸路径 | OK，1 个结果 |
| `"C:\...\Win64_x64"`（两端双引号，单一取值） | **FAIL，0 个结果** |
| `  C:\...\Win64_x64`（前导空格） | **FAIL，0 个结果** |
| 尾部空格 / 引号+空格 | FAIL，0 个结果 |
| `dir;dir`（分号分隔多值） | OK |
| `"dir";"dir"`（分号分隔多值带引号） | OK |

被切成的实际内容：`['"C', '\\Users\\...\\Win64_x64"']`。注意分号分隔的多值路径不受影响（走上一分支并逐段 `strip`）—— **只有「单一取值 + 引号/空格」这一种写法会静默返回空**。MVS 默认就装在 `C:\Program Files (x86)\...`（含空格和括号），现场手写 `GENICAM_GENTL64_PATH` 时加引号是很自然的动作。

**定级说明**：定为 P2 而非 P0，因为 `_VENDOR_CTI_GLOBS`（`camera.py:43-53`）和 `_registry_mvs_roots()`（`camera.py:202`）的兜底搜索在正常安装的机器上会补上，症状被掩盖。只有在非常规安装路径 + 手写环境变量的组合下才会暴露。

**修复建议**：先 `raw.strip()`、再去掉成对的引号，然后判断盘符；或改用 `os.pathsep` 分隔并复用现有的逐段处理逻辑。

### P3

#### A3. `_score_roughness` 在 `cv_max` 处断层（60 分 → 0 分）

**位置**：`core/quality.py:290-292`

docstring（`quality.py:285`）明写「CV = cv_max → 60 分」，实现却是另一回事：

| 输入 | 得分 |
|---|---|
| 0.3499 | 60.01 |
| 0.35（= cv_max） | **0.0** |
| 0.36 | 0.0 |

`mean_cv >= cv_max` 分支用 `100*(1-cv/cv_max)`（斜率不同），阈值右侧立刻归零。粗糙度权重 0.30 → **18 分的总分跳变**，足以单独翻转 OK/NG。

**修复建议**：统一为 `100 - (cv/cv_max)*40`，并让 `>= cv_max` 延续同一斜率（或明确改为在 100% 处饱和）。

#### A4. `_score_oxidation` 在 `max_pct` 处断层（60 分 → 50 分）

**位置**：`core/quality.py:309-311`

| 输入 | 得分 |
|---|---|
| 4.99% | 60.08 |
| 5.0%（= `oxidation_max_pct`） | **50.0** |

第二分支是 `100 - pct*10`（斜率 10），与第一段的 40/5 = 8 不一致；且同一分支里的 `min(..., 60)` 钳位在 `pct >= 5` 时**永远不生效**（死代码）。`_score_embedding`（`quality.py:322-323`）、`_score_unroughened`（`quality.py:334-335`）有完全相同的结构问题。

**修复建议**：四个评分函数抽出一个公共实现，消除结构重复 —— 这是同一处设计缺陷的四个副本。

#### A5. `direction_consistency_min` 是死配置

**位置**：`core/quality.py:111-113`（读取）→ `quality.py:269`（仅重导出到 `detail`）

**实测**（同一张图，`direction_consistency_min` 取 0.1 / 0.6 / 0.9）：

```
min=0.1  → 总分=65.5  预警=['roughness 评分偏低: 0.0/100']  detail阈值=0.1
min=0.6  → 总分=65.5  预警=['roughness 评分偏低: 0.0/100']  detail阈值=0.6
min=0.9  → 总分=65.5  预警=['roughness 评分偏低: 0.0/100']  detail阈值=0.9
```

总分、分项、预警三者**完全不变** —— 唯一跟着变的是 `detail['thresholds']['direction_min']` 里回显的那个值本身（即「改了什么就回显什么」，但没有任何计算用它）。`_score_direction()` 只用 DCI 本身，全模块没有任何地方读这个阈值。

`default.yaml:121` 的注释把它描述成「锚纹方向一致性下限」，现场据此调参不会产生任何效果。

**修复建议**：要么在 `_score_direction` 里真正使用（低于下限直接扣到 0 或触发 NG），要么从配置和 `detail` 里删掉。

#### A6. `report.detail['weights']` 与 `self.weights` 共享同一可变对象

**位置**：`core/quality.py:266`

```python
report.detail = {
    "scores": scores,
    "weights": self.weights,     # 没有拷贝
    ...
}
```

**实测**（热力图均值取 0.005，使粗糙度分 = 100，这样权重变化才看得见）：

```
assess 前  assessor.weights['roughness'] = 0.3
B1 总分 = 98.5（粗糙度分 100.0）
detail['weights'] is assessor.weights = True
从报告里改 detail['weights']['roughness'] = 0.99
  → assessor.weights = {'roughness': 0.99, ...}
下一块板卡 B2 总分 = 167.5    对照（全新 assessor）B2 总分 = 98.5
→ 污染生效 = True（差 +69.0 分）
```

注意 `167.5` 已经**超过 100 分上限** —— 因为权重和不再等于 1.0，评分体系的量纲随之失效。一块板卡的报告被改动，会静默污染该评估器之后**所有**板卡的权重分配，且总分可以突破 100。

**可达性**：现有调用点只**读**这个字段（`ui/main_window.py:478`），不写。所以这是「public API 返回了内部可变对象」，当前不触发，但任何一次「顺手改一下展示用的权重」都会造成上述全局污染。

**修复建议**：`"weights": dict(self.weights)`。

#### B1. `to_json` 输出 NaN 字面量（非 RFC 8259）

**位置**：`core/reporter.py:97`

`json.dumps(..., ensure_ascii=False)` 未关闭 `allow_nan`。当 `quality.overall_score` 为 NaN 时输出裸 `NaN`，**不是合法 JSON**，严格解析器（含多数工业 MES 接口）会拒绝。

**修复建议**：`allow_nan=False` + 上游保证分数有限；或在写 NaN 前替换为 `null` 并记 warning。

#### B2. `to_text` 在 `quality=None` 时崩溃（与 `to_dict`/`to_json` 行为不一致）

**位置**：`core/reporter.py:111`、`115-120`

`to_dict()` 逐字段守卫（`q.board_id if q else ""`），`to_text()` 直接访问 `q.overall_score`、`q.roughness_uniformity` 等 → `AttributeError`。

而 `quality=None` 是**合法且已声明的状态**：`InspectionResult.quality` 的默认值就是 `None`（`core/pipeline.py:28`），`summary()`（`core/pipeline.py:57`）也做了守卫。同一份结果，`to_dict` 安全、`to_text` 崩溃。

**修复建议**：`to_text` 复刻 `to_dict` 的守卫方式（缺失时打 `N/A`）。

#### E3. `validate_config_path(None)` → `AttributeError`

**位置**：`utils/validators.py:89`，`.lower()` 未加保护。docstring 承诺 `ValueError`。

**修复建议**：入口加类型检查，非 `str` 一律 `ValueError`。

## 5. 范围外与残余风险
#### A2. 缺失 DCI 按最差情况评分（公开 API 的契约陷阱）

**位置**：`core/quality.py:180-181`，配合 `quality.py:45` 的默认值

```python

...
if direction_consistency is not None:
    report.direction_consistency = direction_consistency
# DCI 为 None 时保持 1.0
```

`_score_direction()` 是 `100 - dci*100`，于是缺 DCI → 0 分 → 总扣 15 分。对照：缺失热力图时走 `quality.py:175-177`，**给满分 100**。同一个函数，两个可选参数缺失时的方向完全相反。

**实测**（同一块板、同样缺陷，只差传不传 DCI）：

|---|---|---|---|
| 传 DCI（0.0032） | 0.0032 | 70.0 | OK |
| 不传 DCI（`None`） | **1.0000** | **55.0** | **NG** |

同一个输入，漏传一个声明为可选（`Optional[float] = None`）的参数，总分掉 15.0 分并翻转判定。

**可达性（重要）**：已核查全部 4 个生产调用点 —— `core/pipeline.py:198`、`ui/workers.py:86`、`main.py:169`、`core/quality.py:355`（`batch_assess`）—— **都传入了真实 DCI 值**。同时实测 `TextureAnalyzer.direction_consistency()` 在正常面、完全平坦面、2×2 极小图、纯黑、纯白五种输入下均返回浮点数，**不会返回 `None`**。

## 9. 后续修复与性能改进（2026-09-20 补记）

本节补记报告交付后的一次改动：把「相机预览时无法检测」查到底，顺带修掉一个
UI 缺陷，并把单帧检测耗时压到原来的约 1/5。改动在
`feature/gabor-accel-and-snapshot-detect` 分支上。

### 9.1 现象与三层原因

现象：进入实时预览后，「开始检测」按钮是灰的。

| 层次 | 原因 | 位置 |
|---|---|---|
| 直接原因 | 预览成功回调里显式禁用了按钮 | `ui/main_window.py` `_on_live_opened()` |
| 根本原因 | 相机分辨率下单帧完整检测要 **108.6 s**，而预览每帧的轻量 GLCM 只要 **6.6 ms** | `core/texture.py` |
| 设计原因 | 预览与检测都会写工艺面板，同时跑数值会来回跳 | `toggle_live_mode()` 的 docstring |

第三层不是借口而是真实约束；第一层是它的实现方式。所以要让预览能检测，
必须先把第二层解决。

### 9.2 瓶颈拆解

在相机配置分辨率 2448×2048 下拆解 texture 阶段的 96.9 s：

| 子步骤 | 耗时 | 占比 |
|---|---|---|
| `glcm.compute`（256 级 × 12 组合） | 73.7 ms | 0.1% |
| `lbp.multi_radius_histogram` | 2603.7 ms | 2.7% |
| **`gabor.feature_vector`** | **47098.8 ms** | **48.6%** |
| `compute_local_entropy` | 177.5 ms | 0.2% |
| `compute_cv_heatmap` | 248.0 ms | 0.3% |
| **`direction_consistency`** | **46715.0 ms** | **48.2%** |
| 六项之和 | 96916.6 ms | |

两趟 Gabor 各遍历 72 个滤波核，合计 **144 次 `scipy.signal.convolve2d`**，
占 texture 阶段的 96.8%。`core/texture.py` 里也只有 Gabor 用 scipy，
其余全部走 `cv2.filter2D`。

### 9.3 改动一：卷积换实现（等价性可证）

`cv2.filter2D` 替代 `scipy.signal.convolve2d`，两处必须同时对齐，
否则结果是**错的而不是慢的**：

* `filter2D` 算相关、`convolve2d` 算卷积 → 核要翻转；
* scipy 的 `boundary="symm"`（边缘样本重复）对应 cv2 的 `BORDER_REFLECT`；
  少一像素的 `BORDER_REFLECT_101` 是 scipy 的 `reflect`，不是它。

单核逐点对照（2448×2048，含边界带单独比对）：

| 核尺寸 | scipy | cv2 | 加速 | max\|Δ\| 全域 | 边界带 |
|---|---|---|---|---|---|
| 7×7 | 0.269 s | 0.013 s | 21.3× | 4.2e-16 | 2.8e-16 |
| 11×11 | 0.594 s | 0.048 s | 12.3× | 1.0e-15 | 8.9e-16 |
| 15×15 | 0.998 s | 0.053 s | 19.0× | 5.6e-16 | 4.4e-16 |

### 9.4 改动二：去掉重复的第二趟 Gabor（逐位等价）

`_build_kernels` 的嵌套顺序与 `direction_consistency` 内部的循环顺序一致，
两者遍历的是同一批核、同一张图，第二趟是纯重算。改为由 `scan()` 单趟产出
特征向量与各方向能量，DCI 复用后者的结果。

断言用 `==` 而非 `allclose`：

```
原始 DCI (再卷一遍)  = 0.0025876540158881662
复用 DCI (推导)      = 0.0025876540158881662
逐位相同 ( == )      = True
绝对差               = 0.000e+00
feature_vector 逐位相同 = True   max|Δ| = 0.000e+00
```

顺带解决一个内存问题：`feature_vector` 原先经 `filter()` 会把 72 张响应图
全部留在内存（2448×2048 float64 约 **2.9 GB**），而它只需要每张的 mean 和
std。`scan()` 逐张归约后即丢弃，峰值降到一张。

### 9.5 相机真实分辨率实测

| | 改前 | 改后 |
|---|---|---|
| texture 阶段 | 97059 ms | **7687 ms** |
| 整条检测 | 108.6 s | **20.8 s** |

与改动前实测记录的基线逐字段对拍：

| 字段 | 改后 | 基线 | 差 |
|---|---|---|---|
| `overall_score` | 55 | 55 | 0 |
| `ok_ng` | False | False | — |
| 缺陷数 / 类别序列 | 433 | 433 | 一致 |
| `roughness_std` | 0.96329801487349387 | 0.96329801487349398 | 1.1e-16 |
| `direction_consistency` | 0.00048933866524802829 | 0.00048933866524802797 | 3.3e-19 |

**残余风险（须如实说明）**：数值差在 1e-14 相对量级而非零。绝大多数样本
无影响，但**恰好卡在阈值边界**的样本理论上可能翻转判定。上线前应拿同一批
样本跑一遍两个后端比对判定结果 —— 这需要真实样本，本次未做。

**仍未实时**：20.8 s 足以支撑「预览 → 抓拍 → 等结果」的按需检测，
但不足以逐帧。要压到 1～2 s 需降分辨率或削减滤波器组合（72 → 12 之类），
那会改变特征值分布，**必须先完成 §5.4 所述的阈值重标定**。

### 9.6 改动三：一个新发现的 UI 缺陷（P2）

在线模式下 `_set_mode()` 把按钮文案改成「📷 拍照」，但该按钮唯一的槽函数
始终是 `load_image`（打开 `QFileDialog`）—— **按「拍照」弹出的是文件选择框**，
不是从相机抓帧。这也是用户无法把预览画面送入检测路径的直接原因之一。

修复：`_on_load_btn()` 按模式分派（离线选文件、在线抓拍），文案与分派同源；
并让启动时的文案跟随 `config.system.mode`（此前配置为在线模式时仍显示
「加载图像」）。

另新增 `_capture_frame()`：**复制**当前帧 → 停预览 → 走与离线完全相同的路径。
复制是必需的 —— `current_raw_image` 会被下一帧覆盖，而检测跑在后台线程里。
抓拍即停预览是刻意取舍：这样两条路径不会同时写工艺面板，无需额外互斥逻辑；
代价是检测那约 21 s 内相机是停的。
